# 架构决策记录（ADR）

版本：0.1 · 2026-10-14

## 为什么需要 ADR

仓库里已有大量**评估型**文档（`ARCHITECTURE_REVIEW`、`RESEARCH_WORKFLOW_REVIEW`），它们记录"这一轮发现了什么"。缺的是**决策型**记录：某个选择为什么这么做、当时否掉了什么、什么条件下应该重新考虑。

没有 ADR 的后果很具体：半年后有人（包括你自己）会觉得"为什么不用 CRDT"，然后重新论证一遍，或者更糟——直接改掉而不知道代价。

## 规则

1. **一个决策一个文件**，编号连续，不复用。
2. **写法**：状态、背景、决策、后果（正面/负面）、被否掉的方案及原因。
3. **状态**：`提议` / `已接受` / `已废弃` / `被 ADR-xxxx 取代`。
4. **不修改已接受的 ADR 的决策内容**。要改就写新的 ADR 并标记取代关系。这和历史迁移不改含义是同一条原则。
5. **代价必须写**。只写好处的 ADR 没有价值。

## 模板

```markdown
# ADR-XXXX：标题

- 状态：已接受
- 日期：YYYY-MM-DD
- 相关：[数据模型](../DATA_MODEL.md)

## 背景
促使这个决策的具体约束。引用实际代码或文档，不写抽象原则。

## 决策
一句话说清选了什么。

## 后果
**正面**：……
**负面**：……（必须写）

## 被否掉的方案
- 方案 A：否掉的原因
- 方案 B：否掉的原因

## 重新考虑的条件
什么情况下应该回来改这个决策。
```
