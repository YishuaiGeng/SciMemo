## 1. 存储

| 能力 | 浏览器 | Windows | macOS | Android | iOS |
|---|---|---|---|---|---|
| 持久化实现 | IndexedDB 🟡 | SQLite ✅ CI 编译 | SQLite ✅ 已编译 | SQLite ⛔ | SQLite ⛔ |
| 重启后数据存在 | 🟡 未测 | ✅ CI 存储层测试（非端到端） | ✅ 存储层测试（非端到端） | ⛔ | ⛔ |
| CAS 冲突检测 | 🟡 已编码 | 🟡 已编码 | 🟡 已编码 | ⛔ | ⛔ |
| 一致性读快照 | 单事务天然满足 | 🟡 已编码未编译 | ✅ 读事务 + 测试 | ⛔ | ⛔ |
| 配额/容量上限 | 浏览器配额，行为因浏览器而异 | 30 MB 工作区上限 ⛔ 未优化 | 同左 | ⛔ | ⛔ |
| 增量提交 | ⛔ | ⛔ | ⛔ | ⛔ | ⛔ |
| 清理风险 | **用户清理站点数据会丢** | 无 | 无 | **系统可能清理** | **长期未打开会清理** |

**核心结论**：**手机端永远不能是唯一副本**。这不是待解决的问题，是设计前提。桌面端为权威，手机为捕获与查阅客户端。

## 2. 文件导出与导入

| 能力 | 浏览器 | Windows | macOS | Android | iOS |
|---|---|---|---|---|---|

| 原生"另存为"对话框 | 🚫 不适用 | 🟡 已编码未编译 | 🟡 已编译，未点击验证 | ⛔ | ⛔ |

**当前 token 只驻留内存**（设置页）。这意味着：**每次重启都要重新输入**。它是安全友好的，但对"每天用"的软件是严重摩擦。设备级凭据存储是 `SM-102`，优先级应高于多数 UI 工作——**它同时是手机端的前置条件**。

## 6. 处理现状与优先次序

**M1 需要真实验证（🟡 → ✅）**，按 `ROADMAP.md`：

1. Windows 与 macOS 各自安装、启动、退出并重启（`SM-002`）
2. 端到端 UI 关键路径（`SM-003`）
3. 原生备份 UX 与恢复演练（`SM-004`）
4. 异常退出后的草稿找回（`SM-005`）
5. SQLite 一致性读快照（`SM-010`）

**M2 需要实现（⛔ → ✅）**：

6. 设备级令牌与撤销（`SM-102`）— 手机端前置条件
7. 自动同步与失败退避（`SM-101`）
8. 增量提交与性能基线（`SM-008`）

**暂不投入**：Docker 镜像、Linux 打包、端到端加密、附件。

## 7. 平台验证的记录要求

每次真机验收必须记录，不得只写"通过"：

| 项 | 内容 |
|---|---|
| 系统与版本 | 具体到 `Windows 11 23H2` / `macOS 15.3` 这样的粒度 |
| 安装方式 | 安装包 / 侧载 / `npm run desktop:dev` |
| 数据路径 | SQLite 文件实际位置 |
| 重启验证 | 关闭 → 重开 → 数据仍在（附截图或输出） |
| 失败项 | 如实列出，不合并进"部分通过" |

结果写入 [TEST_REPORT](TEST_REPORT.md)。native 与 device 测试必须**分别报告**，不得用 macOS 浏览器检查代替原生壳验收（KNOWN_LIMITATIONS #2 已明确）。
