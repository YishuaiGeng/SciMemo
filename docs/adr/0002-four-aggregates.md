# ADR-0002：四个顶层聚合，Paper 为唯一同步聚合

- 状态：已接受
- 日期：2026-10-13
- 相关：[数据模型](../DATA_MODEL.md)、[架构蓝图](../ARCHITECTURE.md) §4

## 背景

科研记录天然是关系型的：一篇稿件有多次投稿，每次投稿有多个事件，事件可能关联日程，日程可能关联会议届次。

同步的最小单位需要选择：是让 `Submission`、`SubmissionEvent` 各自成为可独立同步的文档，还是让它们内嵌在 `Paper` 里？

## 决策

四个顶层文档类型：`paper`、`note`、`venue`、`deadline`。

`Submission` 与 `SubmissionEvent` **内嵌**于 `Paper.data`；`ConferenceEdition` **内嵌**于 `Venue.data`。

跨聚合引用一律用 UUID 弱引用。

## 后果

**正面**

- **一次投稿操作不可能半成功**。追加事件 = 修改一个 `Paper` 文档 = 一个事务、一个版本、一次网络写入。这消除了"事件写成功了但稿件没更新"这类最难排查的状态。
- 历史保留是实现层的事：整个 `Paper` 一次提交，转投时旧 `Submission` 天然留存。
- 撤销/冲突的单位与用户心智一致——"这篇稿件"。

**负面**

- **冲突粒度粗**。两台设备分别改同一篇稿件的不同字段（A 改 `nextAction`，B 追加了一个 reviewer 事件）也会产生冲突。这是为原子性付出的明确代价，记录在 [同步协议](../SYNC_PROTOCOL.md) §5。
- `Paper` 文档会随时间增长（多次投稿 × 多个事件），单文档 500000 字节上限是真实约束。
- 不能只同步一篇稿件的部分历史（例如"只要最近一次投稿"）。

## 被否掉的方案

- **完全规范化为独立表/独立文档**：每次投稿涉及 3+ 个网络写入，部分失败无法向用户解释，且需要在协议层设计依赖顺序。
- **CRDT / 字段级合并**：见 [ADR-0003](0003-manual-sync-no-crdt.md)。
- **Project → Paper → Submission 三级层次**：AGENTS.md 明确禁止强制项目层级。多数研究者的"项目"概念不稳定，强制结构化会劝退随手记录。

## 重新考虑的条件

- 真实使用中出现大量"改不同字段也冲突"的情况，且用户明确认为这是问题（而不是可接受的保守行为）。
- 单篇稿件的文档接近 500000 字节上限。
- 需要多人协作编辑同一稿件。
