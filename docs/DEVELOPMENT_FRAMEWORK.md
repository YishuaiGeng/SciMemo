## 1. 产品边界

定位：**以论文投稿记录为主线，同时容纳独立的科研创新点随笔与期刊会议信息的个人科研手账。**

主要用户是同时推进多篇论文的个人研究者。第一版不考虑实验室管理员、教学管理、学生管理或多租户机构服务。

必须回答四个问题：我的论文现在在哪个阶段；这一次投稿发生了什么；下一步做什么；此前记下的创新点与投稿目标在哪里。

### 1.1 信息架构

| 入口 | 主要能力 | 与其他模块的关系 |
|---|---|---|
| 我的稿件 | 题名、工作阶段、下一步、投稿经历、归档 | 关联独立随笔、候选目标和日程 |
| 灵感随笔 | 创新点、临时假设、讨论记录、科研杂记 | 可以不关联稿件，也可以关联多个稿件 |
| 期刊会议 | 自己收藏的期刊、会议系列、具体届次 | 为候选目标、实际投稿、截稿事件提供入口 |
| 近期日程 | 投稿截止、修回、个人跟进、会议举办日期 | 日程可独立存在，也可关联稿件或会议届次 |
| 设置与数据 | 导出、空工作区恢复、同步、冲突、回收站 | 不是业务首页 |

“近期会议”首版是用户已收藏会议的日期视图，不是未经核查的自动资讯流。不要宣称已经覆盖所有会议。

### 1.2 使用原则

新建稿件仅要求名称。独立随笔仅要求正文。其他字段按需要补充；未知日期允许留空，不能填入今天制造历史事实。

投稿情况不等于工作阶段。审稿中仍可补实验；一轮拒稿不等于研究结束；归档只影响默认列表。

一篇稿件有多次投稿。转投新增 Submission，同一次投稿中的修回新增 SubmissionEvent。录入时保留目标名称、当时题名及具体届次快照。

## 2. 技术栈与取舍

| 层 | 选型 | 在 SciMemo 中的职责 |
|---|---|---|
| 用户界面 | React 19 + TypeScript | 表单、列表、详情、响应式布局 |
| 前端构建 | Vite 8 | 本地开发与静态资源构建；不用 SSR |
| 桌面与移动壳 | Tauri 2 | Windows/macOS 为首发目标；共用 Android/iOS 入口 |
| 原生本地存储 | Rust + rusqlite + SQLite | 固定工作区、原子事务、持久化与安全导出 |
| 浏览器开发存储 | IndexedDB | 让业务开发不必每次启动原生壳 |
| 可选同步端 | Python + FastAPI + SQLite | 单用户私有工作区的版本化同步 |
| 测试 | Node test runner + pytest | 业务规则、协议、备份与真实 HTTP 流程 |
| 开源工程 | 单仓库 + GitHub Actions + Docker | 小规模维护，不引入大型构建管理工具 |

采用这一组合是本项目的设计选择，不是所有场景下的唯一正确技术栈。业务层与 UI、IPC、HTTP 解耦，是后续替换框架的保护边界。

Tauri 官方列出桌面与移动平台，并提供 Vite 集成与 Rust command 调用方式 [R1–R3]。这不等于已经测试了每个操作系统版本，也不意味着手机端只是缩小桌面页面就完成。[R4]

不采用 Next.js 的原因是当前没有服务端渲染、公开内容 SEO 或在线账户门户的需求；不把 Python 服务捆绑到每个桌面安装包，因为离线 CRUD 不应依赖它。

## 3. 总体架构

```text
React 页面：稿件 / 随笔 / 期刊会议 / 日程
                  │
            WorkspaceService
            业务校验与本地事务
                  │
       ┌──────────┴──────────┐
       │                     │
   浏览器适配器           Tauri 适配器
   IndexedDB             Rust commands
       │                     │
       │                本地 SQLite
       └──────────┬──────────┘
                  │ 主动同步时才调用
             SyncEngine
           outbox / conflict
                  │ HTTPS
        自托管 FastAPI Sync
        SQLite + change log
```

同一份核心逻辑用于电脑与手机。首版不为手机再写一套独立后端或一套不同的数据模型。

**本地优先的验收定义**：未配置服务地址和令牌时，仍能完成新增、编辑、投稿记录、搜索和导出。远程服务失败只能导致同步失败，不能导致本地已保存内容消失。

## 4. 业务模型与存储模型

### 4.1 四个顶层记录类型

Paper、Note、Venue、Deadline 是独立同步记录。Submission 和 SubmissionEvent 是 Paper 内部独立定义的领域类型；ConferenceEdition 是 Venue 内部类型。

这种安排避免初版把一项投稿的状态与事件拆成两个独立网络写入，造成一部分成功、一部分冲突。整篇稿件以一个事务／一个版本同步，代价是并发修改同一篇稿件的不同部分也可能产生冲突。

这是**单用户多设备首版的保守取舍**，不是宣称完全规范化关系数据库或细粒度 CRDT 已经实现。未来如确有大量并行编辑，再改成带依赖的原子多记录操作。

### 4.2 当前物理存储

原生 SQLite 使用 `documents(id, kind, body)` 保存类型化 JSON 文档，`local_meta` 保存本地修订号，`operational_state` 保存 outbox、冲突、同步游标与服务端绑定标识。

浏览器适配器使用一个 IndexedDB 原子事务保存等价工作区。

当前适配器为了便于阅读和验证，采用全工作区读取／提交，SQLite 在事务内重写文档集合。适合开发起步，不应宣传已经为数万条记录和大附件优化。达到性能门槛后，升级为按变更文档增量写入，保持 Driver 接口及测试不变。原生读取的多次 SELECT 目前未包同一读事务，跨进程一致快照仍待修复和验证。

### 4.3 三种版本号不能混用

`schemaVersion` 表示应用数据格式；`localRevision` 用于同机标签页／窗口的乐观并发控制；文档 `version` 是服务端已确认版本，不能依赖本机时钟决定远程覆盖。

## 5. 关键业务流程

### 5.1 新的科研想法

只填写正文 → 存为 Note → 后续补标签／关联稿件。创新点没有强制状态机，也不强迫填写假设、方法、实验设计等模板字段。

### 5.2 新稿件与投稿

创建暂定题名 → 记录工作阶段和下一步 → 收藏候选目标及理由 → 实际提交时新增 Submission → 后续追加事件 → 结束后允许下一轮投稿。

只允许一个未结束的投稿记录是首版的默认产品规则，用于防止误把转投记成同时投稿；它不是对所有学科政策的自动判断。特殊场景可在未来加入明确的覆盖流程，但不能绕过历史保留。

### 5.3 期刊与会议

Journal 与 ConferenceSeries 区分；同一会议的不同年份保存为 Edition。实际投稿保存名称和题名快照，后续编辑官网资料不改写过去投稿。

候选目标、真实投稿目标、某届会议日期是不同概念，界面必须使用不同标签。

### 5.4 日期

未知日期用 null；仅知道某天时用 `precision=date`；知道精确截止时刻时保存带 UTC 偏移的 `at`、IANA 时区和原始说明。

首版用显式偏移输入避免不知不觉采用电脑时区。AoE 示例对应 UTC−12；不能把其他任意会议默认成 AoE。

### 5.5 删除

软删除产生 tombstone 并参与同步。不自动级联删除随笔或其他记录。关联对象被删除时保留其 ID 并提示，不偷偷断开引用。回收站可恢复；永久清除和 tombstone 回收需要单独协议，首版不提供。

## 6. 同步原则

服务端是用户自己的可选服务，不是 SciMemo 的强制账户中心。当前一个部署对应一个个人工作区，令牌用于保护所有同步数据，不实现多租户。

每条本地变更与 outbox 在同一个事务提交；上传包含不可变操作 ID 与 baseVersion；服务端只有在 baseVersion 匹配时接受。结果确认持久化前，不删除待同步操作。请求重试由幂等 ID 防止重复提交。

下载使用单调递增 change-log cursor；删除同样下载。记录冲突保留本机与远端版本，等待用户选择。双方历史仍能导出。

一个服务端随机标识绑定工作区。标识变化、游标领先服务端或协议异常时停止，不自动切换为新数据库。恢复服务端旧备份时必须停机并轮换标识；这是明确的运维步骤。

当前 UI 只提供手动同步。后台同步、离线自动重试退避、自动发现设备和附件同步不属于已完成功能。

本轮上传按完整请求 UTF-8 字节组批（每轮最多4MB/100条），其余操作留在 outbox；界面提示继续同步。ACK与下载分页在核心层核对身份、正文、版本、序号和游标，异常整轮不提交。网络期间仍持有业务服务队列；历史下载最多100页，长历史的检查点推进尚未实现，不能宣称无限容量或同步期间保存无阻塞。

## 7. 备份与迁移

用户便携导出：JSON 保存全部业务记录、嵌套投稿历史、关联 ID、删除记录及冲突档案；随笔可导出 Markdown，稿件列表可导出 CSV，日程可导出 ICS。

便携导入只允许空且未绑定服务端的工作区，保留业务 ID，重置服务端版本／游标并重新建立 outbox。它不是把另一台设备的所有内部状态原样复制过来。

同步不等于备份。同步也会传播删除。SQLite 物理备份使用 SQLite backup API，不直接复制写入中的主数据库文件 [R5]。服务端脚本会做完整性检查。

JSON 不含二进制附件，因为当前尚未实现附件管理。不能在当前版本宣传“导出已包含附件”。

## 8. UI 开发规范

首屏是稿件列表，使用阶段、当前投稿情况和下一步，不使用虚构的百分比完成度。

随笔以简洁卡片展示，正文是普通文本／Markdown 源文。输入通过 React 转义；不渲染任意 HTML，不从笔记加载脚本。

桌面侧边导航；窄屏使用底部四入口，设置保留在顶栏。表单使用原生 dialog、键盘焦点和字段标签；关闭存在输入的弹窗时提示放弃。

样式使用系统字体、CSS 变量与少量组件；没有网络字体、图标 CDN 或运行时远程资源。当前图标仅是开发占位，正式视觉品牌另行设计。

## 9. 安全与隐私边界

默认不联网、不上传、不采集遥测。同步地址与令牌由用户主动输入；当前令牌仅驻留设置页内存。

原生客户端只暴露固定工作区读取、原子提交和固定导出目录写入，不向 UI 暴露任意 SQL、任意路径写入或 shell。

生产同步必须经 HTTPS，CORS 使用明确来源列表，限制请求体、记录大小和批次数量，服务器固定 SQL 参数化处理。

当前不加密本地 SQLite，也不提供端到端加密。拥有本机文件权限或服务端数据库权限的人可以读取数据。发布前需增加自动备份、凭据安全存储、依赖安全审计、反向代理限流、异常日志脱敏及恢复演练。

不能把“开源”“本地保存”“自托管”包装成已经经过安全审计。

## 10. 开发顺序与完成定义

第一步：在 Windows/macOS 上安装依赖、通过完整 TypeScript 检查与 Web 构建；用虚构数据做 UI 冒烟测试。

第二步：编译 Tauri 桌面壳，验证 SQLite 路径、重启持久化、导出位置、回收站、跨窗口冲突与应用升级迁移。

第三步：用隔离的测试工作区验证真实双端同步，覆盖离线修改、并发更新、网络丢包、删除和服务端回滚。

第四步：完成 Android/iOS 工程初始化、文件访问与网络策略适配，再做真机测试；不是只凭响应式页面宣布手机 APP 已完成。

第五步：补齐公开发行前的备份、更新与签名机制。只有这些通过，才把版本从 dev 改为 alpha/beta。

具体任务见 ROADMAP.md。暂不设虚假的日程估计，以可验收的里程碑作为进度单位。

## 11. 不扩张清单

不做 Zotero 式文献抓取和引用库；不做 LaTeX 编辑器；不做实验调度平台；不做教师学生管理；不做复杂团队权限；不做 AI 必需品；不默认接入 Gmail 或抓取投稿网站。

将来增加智能功能时，先做“用户粘贴文本 → 提取候选信息 → 人工确认”，禁止自动把不确定的邮件解释写成正式状态。
