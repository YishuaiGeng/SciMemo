# ADR-0008：自托管同步服务，不做账户中心

- 状态：已接受
- 日期：2026-10-13
- 相关：[同步协议](../SYNC_PROTOCOL.md)、[SECURITY.md](../../SECURITY.md)

## 背景

多设备同步需要服务端。可选路线：自建账户中心（注册、登录、多租户）、第三方后端即服务（Firebase/Supabase）、或用户自托管单工作区服务。

AGENTS.md 的核心承诺是"No mandatory account, server, AI API key or internet connection for local record operations"，且"不引入遥测"。

`server/` 当前是 FastAPI + SQLite，单工作区共享令牌，Docker 部署，`SCIMEMO_SYNC_TOKEN` 至少 32 字符。

## 决策

同步服务是**用户自己的可选组件**：

- 一个部署 = 一个个人工作区，**不做多租户**。
- Bearer 令牌保护全部数据；远程必须 HTTPS，`localhost` 允许 HTTP 调试。
- 服务端持有变更日志与 `serverId`；客户端凭 `cursor` 增量拉取。
- **不提供注册、托管、账号恢复**。
- 服务端可读取正文；**不承诺端到端加密**。
- 不随桌面安装包捆绑 Python 服务运行（离线 CRUD 不得依赖它）。

## 后果

**正面**

- 用户的数据不经过任何第三方服务器。对科研未发表内容，这是可向合作者交代的隐私立场。
- 无账户系统 ⇒ 无密码找回、无会话管理、无用户枚举攻击面、无隐私政策与合规负担。
- 服务端可以很简单：单文件 FastAPI + SQLite，可审计。
- 与"本地优先"一致——不开同步也能完整使用。

**负面**

- **用户要有服务器**。对多数研究者，这是真实门槛，意味着同步实际上只有技术型用户会用。
- **令牌形态是当前最大弱点**：单工作区共享令牌无法按设备撤销（丢一台设备就要换令牌并重配所有设备），且令牌只驻留内存、每次重启重输（`Settings.tsx`）。
- 服务端能读正文。没有端到端加密（`SM-106` 之前不应宣传隐私保护强度）。
- 公网部署的安全责任在用户，反向代理、限流、日志脱敏都需要用户自己配置（`SM-106` 未完成）。
- 服务端备份与恢复要靠用户自己理解 `serverId` 轮换语义（[同步协议](../SYNC_PROTOCOL.md) §6）。

## 被否掉的方案

- **自建账户中心 + 托管服务**：与"不需要账号"的核心承诺直接冲突，且引入运维、合规、成本与数据泄露责任。一个个人项目承担不起。
- **Firebase / Supabase 等 BaaS**：把未发表研究内容交给第三方，且需要用户注册账号；与隐私立场冲突。
- **只做本地文件同步（iCloud/Dropbox 目录）**：诱人且零服务端，但会让同一工作区被两个进程同时写入，直接破坏 CAS 原子提交的前提；SQLite 文件本身也不适合放在同步盘上。
- **P2P / LAN 直连同步**：设备发现、NAT 穿透、离线队列的复杂度远超收益。

## 重新考虑的条件

- 出现大量用户明确表示"没有服务器但需要多设备"——届时应考虑**端到端加密 + 可选托管**作为独立产品线，而不是放弃自托管。
- `SM-102` 完成后若设备级令牌仍不够（例如需要审计日志、细粒度共享），再评估是否升级协议。
- 若要支持共享工作区（合作者共同记录），必须先写新 ADR——当前模型是单用户的，改成多用户会波及整个权限与冲突设计。
