# SciMemo 科研流程评估与功能取舍

评估日期：2026-10-13。依据是仓库中的领域类型、规则、页面、备份与同步实现，以及本轮稿件关联日程改动。本文是产品与流程评估，不代表原生安装包、真实设备或科研资料安全已经验收；实际执行的检查以 [TEST_REPORT](TEST_REPORT.md) 为准。

## 1. 项目是否完善

**SciMemo 已有清楚的产品边界和可用的核心模型，但还未达到“可以放心作为日常科研资料唯一保管处”的成熟度。** 主要问题是记录后的纠错、跨模块行动衔接和日常数据保护，不是模块数量不足。

最有价值的设计已经存在：稿件工作阶段与投稿状态分离；同一稿件保存多次投稿；修回留在原投稿里；转投保留旧目标和当时题名；独立想法不必关联稿件；未知历史日期可以为空；日期级日程不虚构精确截止时刻；删除与同步冲突保留可恢复的内容。这些比再增加几个“科研管理”页面更接近个人研究者的真实需求。

但“能新增”不等于“流程闭环”：用户会录错最终状态、先不知道日期、收到延期、改投新届会议、重新解释旧实验。当前投稿事件只能追加，已有事件和投稿元信息没有补填或纠错入口；会议届次只能追加；跨模块关联虽存了 ID，部分页面未充分呈现；自动备份和异常退出后的草稿恢复尚未实现。应先补这些日常操作。

本轮新增了稿件详情的“关联日程”，可查看、编辑关联记录，并从稿件内创建修回截止或个人跟进，减少记完修回后再离开稿件重新选择关联对象的步骤。新日程仍由用户填写日期，不把通知录入日当作截止日。界面也明确告知：已保存的投稿与事件暂不支持修改或补填，避免原先“所有日期都可补录”的过度承诺。

本轮还加入设置页只读关联审计、业务服务命令与保存边界加固，保留既有候选priority，并修复同步组批与双端验证问题。详细实现及未完成的原生/同步设计见 [架构评估](ARCHITECTURE_REVIEW.md)。

## 2. “覆盖科研流程”的正确含义

SciMemo 应覆盖个人科研全流程的**记录、决策、下一步和回看**，并保留外部证据的入口。它无需亲自执行文献检索、实验、统计分析、写作排版和投稿网站操作。

研究通常不是单向流水线：文献发现会推翻问题，负面实验会改变假设，审稿会要求补实验，拒稿后可能重构贡献。当前 `stage` 是研究者对工作位置的简要标记，不应变成必须逐关通过的审批流；`accepted` 是一次投稿的结束，也不意味着校样、公开发表和资料整理全部完成。

继续保持四个业务入口：稿件、独立想法／随笔、期刊会议、日期。研究问题、实验决定、审稿回应和复盘可以先由可选 Note 模板表达；不要求先建项目、填研究框架、配置服务器或开启 AI 才能记录一个想法。

## 3. 流程矩阵

“已覆盖”表示当前源码已有对应能力，不代表所有平台和交互均完成实测。“最小方案”中的建议，除明确说明本轮新增外，均为后续工作。

|---|---|---|---|---|
| 想法捕获 | Note 只要求正文，可独立存在，可置顶、加标签、关联多个稿件 | 缺少从想法直接建立稿件的快捷入口；意外退出可能丢失未保存输入 | 保持自由记录；可选“由此创建稿件”，保留原 Note，并由用户确认关联；增加本机草稿恢复 | 无稿件也能保存；新建稿件后原想法未被移动或删除；异常关闭后能恢复尚未提交的草稿 |
| 问题论证与可行性 | 稿件摘要、下一步与独立随笔可承载判断 | 没有帮助研究者区分假设、已有证据和待验证问题的模板 | 提供可选正文模板：研究问题、价值、已有证据、最大不确定性、最小验证、继续／暂停理由 | 不使用模板仍可保存；结论改变时保留先前判断及变更理由，不虚构“完成百分比” |

| 实验设计与结果判断 | `experiments` 阶段、progress Note、下一步可记录进度 | 不管理实验执行、数据集版本、统计检验或复现环境；没有结构化的负面结果入口 | 可选 Note 模板记录假设、方案、代码提交、数据版本、结果路径、局限与决定；原始实验留在已有工具 | 用户能回看“为什么换方案／暂停”；实验失败也能独立记录；不要求把大文件搬入 SciMemo |
| 写作与投稿准备 | 写作／修改阶段、摘要、下一步、候选目标和理由 | 缺少投稿前检查清单和外部稿件版本约定 | 可选 Note 清单记录格式、匿名、作者确认、伦理／数据声明、补充材料、cover letter、待提交文件版本；按学科自行调整 | 清单可不使用；不同投稿有可识别的清单版本；勾选清单不会自动把稿件标成已投稿 |
| 期刊／会议筛选 | Venue、会议届次、官网／投稿入口、核查日期；候选目标有理由和priority，本轮保留既有priority | 无显式排序交互，已有届次不能编辑 | 后续允许原ID上编辑届次与显式目标排序；动态规则用备注保留官方来源 | 编辑稿件摘要不改变目标顺序；更正届次官网后旧投稿快照仍保留；不把候选目标显示为实际投稿 |
| 实际投稿 | 新增 Submission，保存目标名称、当时题名、编号、可空投稿日；只允许一次未结束投稿 | 已保存日期、编号或目标录错后无修正入口；无外部稿件版本快照字段 | 当前先明确限制；后续加入保留原值的修订记录；提交版本可先在关联 Note 写明 | 转投前旧投稿及题名可查；未知日期仍为空；纠错前后值与理由可追溯 |
| 审稿与状态跟进 | 追加编辑处理、审稿、大修、小修等事件，区分发生日期与录入时间 | 补录更早历史事件会成为末条当前状态；没有独立“补历史”语义；没有催询提醒的自动功能 | 分开“记录当前变化”和未来“补录历史／纠错”；跟进日程由用户明确设定 | 补录历史不意外让当前状态倒退；跟进日期清楚标为个人计划，不暗示期刊承诺 |
| 修回与逐条回应 | 修回／重投事件留在同一 Submission；本轮新增稿件关联日程及修回／跟进快捷入口 | 没有审稿意见逐条 response 管理；截止日期需手动记录；事件与特定修回轮次的日程未精确绑定 | 先用一个关联 Note 记录“第几轮／Reviewer／Comment／Response／修改位置／待办”，日程关联稿件；确有查询需求再设计 v2 的轮次标识 | 多轮回应能区分，原意见和最终回应可回看；新建修回日程不自动猜日期；提交修订不会自动把所有日程完成 |
| 拒稿、撤稿与转投 | 终态后新增下一次投稿；过去的事件、目标、题名都保留 | 误录终态后无法纠正；缺少转投复盘和准备提示 | 先在 Note 记录拒稿原因、保留意见、改动计划和新目标理由；历史纠错作为独立能力设计 | 新投稿不覆盖旧对象；研究阶段可继续为 writing／experiments；拒稿不强制归档 |
| 接收、发表与成果复盘 | accepted 终态、finished 工作阶段、归档、普通 Note／Deadline | 无专用 DOI、正式发表日、校样／版权元数据；没有发表后复盘模板 | DOI、公开链接、校样事项、经验先存关联 Note／日程；字段需求稳定后再加可选 v2 元数据 | 接收不自动宣称发表；发表日期未知仍为空；成果整理后可归档，归档仍可搜索和恢复 |
| 日常回看与数据保护 | 稿件列表、下一步、搜索、JSON／Markdown／CSV／ICS、软删除、冲突双方保留；本轮只读关联审计 | 缺少自动备份、备份新鲜度、草稿恢复和真实设备闭环；同步会传播删除 | 备份恢复演练、草稿保护和设备验收；自动备份明确保留策略与错误反馈 | 新工作区恢复完整历史；重启不丢已保存内容；断网可编辑；冲突不静默取舍；备份失败可见 |

## 4. 必须优先补齐的功能

### P0：日常使用的可信度与发布门槛

这些工作属于必要能力；不意味着相关源码当前必然存在缺陷，而是必须通过实测才能形成产品承诺。

1. **保存与恢复可验证。** 完整类型检查、Web 构建、IndexedDB 保存／重开、SQLite 重启持久化、空工作区 JSON 恢复分别验收。不要用 MemoryDriver 测试代替真实存储，也不要用一次 HTTP 模拟代替两台设备。
2. **数据保护闭环。** 保留手动导出；实现可关闭的本地自动备份、保留数量／周期、失败反馈和实际恢复演练。恢复应保留 ID、投稿历史、删除记录和冲突档案；不能把“同步成功”当作“已经备份”。
3. **边界可信。** 校验错误日期、过滤链接打开与导出的不安全协议；保持双端语义一致；冲突保留双方；存储失败明确报错。偏移与IANA时区一致性仍有欠缺，应在真实截止管理验收前完成。
4. **诚实状态。** 界面与文档明确缺少事件补填、系统通知、附件管理和未验收平台；完成一个页面不能自动把开发版改称正式产品。

### P1：科研工作每天会遇到的闭环

1. **历史补录与纠错。** 投稿日期、编号、目标、事件状态／日期都需要可纠正。要先定义修订语义和迁移，再开放编辑入口。
2. **稿件与日期互通。** 本轮已加入稿件内查看／创建／编辑日程；后续补充日程列表中的关联对象名称、返回稿件入口、明确完成操作和失效关联提示。
3. **轻量修回支持。** 优先提供可选逐条 response 与投稿清单模板，原文可导出。暂不引入独立“审稿管理中心”。
4. **已有届次编辑与目标排序。** 保持 ID 稳定，编辑时不重写历史快照，不让修改稿件摘要意外改变候选优先级。
5. **异常退出后的草稿恢复。** 关闭弹窗的放弃确认已有；浏览器崩溃、刷新、原生退出后的恢复仍需单独设计与验证。草稿不是已保存的正式状态或同步事件。
6. **关联审计。** 本轮已有缺失/删除/错误类型/缺少届次的只读检查；后续验收UI并改善关联对象名称展示，保留引用，不自动级联删除。

### P2：有价值，但应按使用证据选择

- 从独立想法创建稿件的快捷操作；按标签、工作阶段和投稿状态筛选。
- 接收后的校样、公开链接、DOI、正式发表日期与经验复盘。先用 Note 验证需求，再决定是否值得增加字段。
- 期刊／会议要求的来源核查记录、近期需要重新确认的信息提示。不能把旧分区、费用或日期当作实时事实。
- 小附件、系统通知、自动同步、设备授权、端到端加密。这些涉及存储、备份、权限或协议，不应只增加一个按钮就宣称完成。
- 用户主动粘贴通知后的候选信息提取。必须预览确认后才能写正式状态，AI 服务失败不影响本地记录。当前不是必需功能。

## 5. 哪些信息先用 Note，哪些需要 v2

**先用可选正文模板：** 研究问题、可行性判断、实验决定、负面结果、投稿清单、逐条审稿回应、转投复盘、DOI／成果链接。现有 Note 足以承载，不要求新增枚举或顶层实体；模板内容是帮助，不是提交门槛。

逐条 response 的最小格式可以是：

```text
稿件／第几轮修回：
审稿人及意见编号：
意见原文：
我们的回应：
修改位置／外部稿件版本：
仍待完成：
```

这能开始使用，但没有结构化的“按审稿人汇总未完成意见”、自动统计回应完成率或将日程绑定到某轮修回。不能把手工模板宣传为上述能力已经实现。

**需要设计 v2 的触发条件：** 用户持续需要精确的修回轮次关联、按意见筛选待办、可检索的正式发表字段、历史修订、外部文件版本标识等。升级时同步修改类型、领域校验、JSON Schema、服务端语义校验、虚构样例、导入／导出和测试，并提供明确迁移；不改变旧迁移的含义。

DOI 和正式发表日期若进入模型，应为可选字段；DOI 不是每种成果都有，接收日不能代替发表日。原 Note 不应在升级时被删除或自动解释成权威元数据。

## 6. 为什么历史纠错不能只是允许改文本

科研手账记录的不只是“当前正确答案”，还包括过去作出决定的背景。直接覆盖旧目标、事件或日期会让转投原因、审稿轮次和设备间修改失去依据；彻底锁死历史又无法修复正常的人为录错。

因此应区分三件事：

- **当前状态变化：** 实际收到新通知，追加一个普通事件。
- **补录历史：** 现在得知过去发生的事实，保存发生日期与本次录入时间，但不自动取代已经确认的当前状态。
- **纠正原记录：** 保存被修订记录的稳定 ID、前后值、理由与修订录入时间，保留原文；终态录错也通过此流程处理。

这些操作仍属于 Paper 聚合，在同一事务保存并随同一文档版本同步。日期可能未知或矛盾，不应按客户端录入时钟决定同步胜负，也不能只对 `occurredOn` 排序来推导最终状态。跨设备冲突仍保留两个版本，由明确的解决流程处理。

不建议本轮为了开放纠错而临时添加一个未版本化字段，或把原终态事件偷偷删掉。应先确定显示规则、重复修订／修订撤销语义和 v1 迁移，再提供操作。

## 7. 不建议加入的功能

不加入强制项目树、学生／教师管理、实验室绩效看板、通用插件市场、微服务拆分、完整 PDF 阅读器、引用管理器、自动抓取投稿网站和默认邮件连接。它们会扩张安全、维护和数据模型负担，同时削弱“个人随时记、先存在本机”的优势。

不把 AI 设为录入、保存、搜索或恢复数据的必要条件；不自动发送催稿邮件；不把候选目标变成替研究者做出的投稿决定；不自动把拒稿标成研究失败，也不把接收当作全部科研工作完成。
