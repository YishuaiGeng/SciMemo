# ADR-0003：手动同步 + 保守冲突，不引入 CRDT

- 状态：已接受
- 日期：2026-10-13
- 相关：[同步协议](../SYNC_PROTOCOL.md)、[ADR-0002](0002-four-aggregates.md)

## 背景

同步的难点不是传输，是**冲突归属**。可选路线从简单到复杂：本机时钟 last-write-wins → 版本号 CAS + 人工解决 → 字段级自动合并 → CRDT（自动收敛）。

AGENTS.md 明确约束："Never use client wall clocks for last-write-wins. Conflicts must preserve both versions."

## 决策

- 服务端持有单调递增的 `doc.version`，客户端上传带 `baseVersion`，**只有版本匹配才接受**。
- 不匹配即冲突，**保留本机与远端两个完整副本**，由用户显式选择。
- 幂等键 `opId` 保证重试不重复提交。
- 删除用带版本的 tombstone 参与同步。
- 冲突单位是**整篇稿件/整条记录**（ADR-0002 的推论）。

## 后果

**正面**

- **双方的原始内容都不会丢**。`Conflict` 对象同时存 `local` 与 `remote`，解决后仍留在冲突存档与备份里。这是对"科研记录不可静默丢失"最直接的保障。
- 不依赖设备时钟，避免了时钟偏差导致的静默覆盖。
- 实现与测试面小：协议可被完整覆盖（当前有冲突、删除、丢 ACK 重放的 HTTP 集成测试）。
- 无崩溃收敛算法的调参与调试负担。

**负面**

- **需要用户做决定**。用户可能不理解冲突界面，或选择后发现自己想要的是两者的结合。缓解手段是提供"先导出完整备份再选"。
- 改同一稿件不同字段也冲突（ADR-0002 的负面后果在此体现）。
- 冲突档案与幂等操作表**只增不减**；tombstone 回收需要设备确认水位，尚未设计（`SM-105`）。
- 手动同步意味着用户必须记得点同步，否则多设备会分叉。自动同步（`SM-101`）能缓解但会放大冲突出现频率。

## 被否掉的方案

- **本机时钟 LWW**：AGENTS.md 禁止。且时区错误的机器会静默吃掉正确的数据。
- **字段级自动合并**：听起来更好，实际需要为每个字段定义合并语义（`submissions[]` 数组怎么合并？追加还是合并？），复杂度高且容易产生用户无法解释的状态。
- **CRDT（Yjs/Automerge 等）**：能自动收敛，但需要把领域模型改造成 CRDT 数据结构，`Paper` 内嵌数组的"显式录入顺序"语义（[数据模型](../DATA_MODEL.md) §2 中 `currentStatus` 取末条）与 CRDT 的无序收敛直接冲突。且引入后无法保证"补录旧日期不改变当前状态"这一业务规则。
- **最后写入的整文档覆盖**：会丢数据。

## 重新考虑的条件

- 真实多设备使用中，冲突频率高到用户放弃使用同步。
- 出现了明确的、可枚举的字段级合并需求（例如"标签取并集"），且用户调研支持。
- 届时也应先考虑**把 `Paper` 拆分**（ADR-0002 重新考虑），而不是直接上 CRDT。
