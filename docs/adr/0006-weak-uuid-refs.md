# ADR-0006：弱 UUID 引用，不级联删除

- 状态：已接受
- 日期：2026-10-13
- 相关：[数据模型](../DATA_MODEL.md) §7、[读模型](../READ_MODEL.md) §3

## 背景

记录之间有多处引用：`Note.paperIds[]`、`Paper.targets[].venueId`、`Submission.venueId/editionId`、`Deadline.paperId/venueId/editionId`。

两种经典处理方式：外键 + 级联删除（关系库思路），或弱引用 + 悬空容忍（分布式思路）。同步场景下还有第三种压力：**关联对象可能只是还没下载到**，不代表它不存在。

## 决策

- 引用存 UUID，**不建立强制外键**，不保证引用的对象当前存在。
- **绝不级联删除**：删除稿件不动随笔，删除期刊不动投稿快照。
- 悬空引用是**正常状态**，不是错误数据。服务端不因关联缺失而拒绝写入。
- 由 `core/read/references.ts` 的 `auditReferences` **只读提示**：区分"已删除""暂不存在（可能未同步完）""类型不符""缺少届次"。
- 删除用 tombstone，可恢复。

## 后果

**正面**

- **删除操作绝不会静默销毁用户没打算删的内容**。删掉一篇初稿不会连带删掉挂在它上面的想法。
- 同步乱序天然安全：先到 `Deadline`、后到 `Paper` 不会报错，读到的时候再解析。
- 恢复备份、跨设备合并时不会因引用完整性问题失败。
- 关联审计是**派生视图**，不新增持久化字段、不新增同步实体，因此不增加冲突面。

**负面**

- **界面必须处理"引用的对象不见了"**。每条关联展示都需要判空，这是持续的开发负担。
- 会出现**用户可见的悬空引用**，需要靠审计页告知，而不是自动修复。用户可能觉得"软件坏了"。
- 无法在存储层保证一致性，只能靠审计发现问题。
- `auditReferences` 目前对"暂未同步到"和"真的不存在"给同一提示，用户可能误判（`KNOWN_LIMITATIONS` #9 承认这点）。

## 被否掉的方案

- **外键 + 级联删除**：与同步冲突彻底不兼容（删除可能来自另一台设备且乱序到达），且违反"不自动销毁内容"的产品原则。
- **级联标记待删 + 用户确认**：更安全但复杂，且在多设备场景下"待删"状态本身也要同步，引入新的状态机。当前用审计页提示已足够。
- **在删除时清理所有引用**（把 ID 从各处移除）：会**改写用户没有编辑过的记录**，并制造大量同步冲突。

## 重新考虑的条件

- 悬空引用在真实使用中频繁出现，且用户无法判断该忽略还是该修复。
- 需要"删除稿件时一并归档其关联笔记"这类明确需求反复出现（届时应做成**显式可选的批量操作**，而不是自动级联）。
- 关联审计的提示精度不足（例如无法区分"未同步"与"已删除"）已成为实际困扰，需要引入引用反向索引。届时应作为派生索引实现，不得成为持久化同步字段。
